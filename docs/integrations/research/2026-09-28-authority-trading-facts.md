# D10/D17/D20 A-share trading facts: primary-source feasibility

Checked 2026-09-28. Research only: no provider is admitted, no production coverage is claimed, and no service or client contract was changed. The two requested VM handoff files (`grpc_handoffs/2026-09-27-d10-daily-bar-suspension-status-vm-handoff.md` and `grpc_handoffs/2026-09-27-d17-d20-authority-trading-facts-vm-handoff.md`) are absent in this checkout; the D10/D17/D20 interpretations below follow the delegation text, not those unseen files.

## Decision

A single **versioned, per-security/per-trading-date status fact** is a reasonable shared seam for D10's target-day inference, D17's trading-eligibility gate and D20's daily-bar gap classification. However, public notice search is **not** sufficient to assert `NotSuspended` on a day without a notice. The [SSE STAR disclosure-operation guide, articles 25–27](https://www.sse.com.cn/lawandrules/guide/stock/kcbxxpljg/c/c_20250425_10777769.shtml) explicitly distinguishes suspension applications accompanying an announcement from independent suspension applications **without** an announcement, including emergency applications. Thus “no announcement” is not a negative status fact. The public [SSE suspension page](https://www.sse.com.cn/disclosure/dealinstruc/suspension/) and [SZSE suspension-notice list](https://www.szse.cn/disclosure/notice/temp/index.html) expose discovery surfaces, but this investigation found no public completion watermark, exhaustive universe declaration, or empty-day attestation on those pages. This is an evidence gap, not proof that such an exchange data product does not exist.

Official technical interfaces suggest a feasible higher-trust route, **conditional on obtaining the data and rights**:

- [SSE's current technical-interface catalogue](https://www.sse.com.cn/services/tradingtech/data/) lists the 2026-09-18 IS124 market-data file-exchange specification and IS120 market-data gateway specifications. A [2026-06 IS124 specification, sections 2.8–2.9](https://www.sse.com.cn/services/tradingtech/development/c/10822594/files/2096257019bf484f9b9935fa73f94721.pdf) describes pre-open product-information files `cpxx0201MMDD.txt`/`cpxx0202MMDD.txt`, including suspended products while excluding products not yet listed or not trading; this is a plausible **daily universe** input, subject to reconciliation with listing records. The [2026 IS120 STEP specification](https://www.sse.com.cn/services/tradingtech/development/c/10816478/files/51a3e4c6b92345689c682448582c019d.pdf) describes `TradingPhaseCode`, including `P` for product suspension; a [published IS124 file specification](https://www.sse.com.cn/services/tradingtech/data/c/10813252/files/454eeb0a88c843cba9410db2bfd6b0c0.pdf) describes per-product normal-trading and listed-status flags. These specifications establish field semantics; they do not establish that this project receives every record or a complete daily file. The newer 2026-09-18 IS124 revision is listed in the catalogue but its PDF timed out in this investigation, so its exact field layout needs separate validation before implementation.
- [SZSE's official new-trading-system FAQ](https://www.szse.cn/www/marketServices/technicalservice/introduce/P020180328467244590967.pdf) says daily security-information files include security status and that static files are distributed through FDEP; during trading, realtime market-state information prevails. [SZSE's technology notice](https://www.szse.cn/marketServices/technicalservice/notice/t20200529_577838.html) also says per-security price-limit parameters are published through static reference files and realtime snapshots. These are specifications/operating guidance, not evidence of a currently provisioned full feed here.
- [BSE's suspension-operation guide](https://www.bse.cn/cxjg_list/200025668.html) specifies application and confirmation procedures, and its [trading-support data-interface specification](https://www.bse.cn/uploads/6/file/public/202209/20220902201701_kas8vw9r25.pdf) includes temporary-suspension announcements. This investigation has **not** validated a current BSE all-security daily status feed, its field mapping, or a public negative-status completeness guarantee. BSE remains unavailable for this fact until proven.

## Proposed evidence boundary, not an admitted schema

Use an explicit `TradingStatusFactV1` concept keyed by `(exchange, security_code, trading_date, session/observation_cutoff)` and distinguish `Tradable`, `Suspended`, `ResumedAt`, `NotYetListed`, `Delisted`, and `Unknown`. Include source type and original exchange file/message identifier, file date/revision, observed-at, event/effective time, immutable raw-file hash, universe/record count, sequence or pagination completion, and coverage window. `Unknown` is not `Tradable`; no rows is not a verified empty day. Intraday status must carry the as-of time, because a pre-open answer cannot promise that no emergency halt will occur later. For historical D20 gaps, preserve the historical cutoff and subsequent corrections instead of rewriting a missing bar into an unquestioned suspension.

The requested downstream acceptance shape is more specific than that abstract seam: D10 needs a `(exchange, six-digit code, asset class, effective date)` result of `Trading`/`Suspended`/`Unknown` **independent of daily bars**; `Trading` on an event-free date requires a complete same-day query (including page exhaustion) or a proven complete market file. An eventual response should carry method/schema/version/request ID, identity/date, source-at (or typed unavailable), observed-at, batch ID, and where applicable original notice/event ID and short summary. A resumption must have a first-trading-day boundary, not merely a notice publication timestamp. D17/D20 must consume the same status evidence rather than independently inferring it from candles. These are handoff acceptance requirements supplied in delegation, not properties verified from exchange sources.

To publish `NotSuspended` for a specified security/date, the producer would need **all** of: (1) an official, licensed exchange status/reference feed for the correct market and session; (2) a complete and authenticated daily snapshot or gap-free realtime sequence with exchange-defined start/end or reconciliation; (3) the security present in the effective-date universe, or separately proved unlisted/delisted; (4) successful parsing of the exact versioned exchange specification, row-count/trailer/checksum and date checks; (5) a cutoff consistent with the consumer's claim; and (6) handling for corrections, emergency intraday halts and feed outage. These are proposed admission controls inferred from the data-flow risk, **not** a claim that any cited exchange already guarantees all six. If a check is missing, return unavailable/partial coverage with explicit reason and provenance. Do not map missing market data, no trades, missing daily bar or a failed HTTP scrape to `Suspended` or `NotSuspended`.

## D17 listing and price-limit facts

The exchanges publish event/rule material, but effective-day eligibility needs a daily per-security reference-state join, not ticker prefixes alone. [SSE's stock list](https://www.sse.com.cn/assortment/stock/list/) separates listed, pending and suspended/terminated securities; [SZSE's stock list](https://www.szse.cn/market/product/stock/list/index.html) and [BSE's code-mapping list](https://www.bse.cn/service/code_mapping.html) are additional public discovery surfaces. [SZSE's exchange-announcement list](https://www.szse.cn/www/disclosure/notice/company/index.html) publishes stock-listing decisions. These pages do not, by themselves, prove a complete historical effective-date universe. Exchange reference files and original listing/termination decisions should be joined and versioned; an absent ticker is not evidence of delisting.

Price-limit *rules* are confirmed but are not an automatically complete per-security *fact*. [SSE's 2026 trading rules](https://www.sse.com.cn/lawandrules/sselawsrules2025/stocks/exchange/c/c_20260424_10816482.shtml), effective 2026-07-06, specify the ordinary 10% limit, STAR 20%, first five IPO trading days without a limit, and other exceptions. [SSE's own revision explanation](https://www.sse.com.cn/aboutus/mediacenter/hotandd/c/c_20260424_10816474.shtml) says main-board risk-warning shares changed from 5% to 10% on that date. [SZSE's 2026 trading rules](https://docs.static.szse.cn/www/lawrules/rule/trade/current/W020260424690713155663.pdf) specify main-board 10%, ChiNext 20%, first five IPO trading days without a limit, relisting/first delisting-arrangement day exceptions and exchange-discretion exceptions. [BSE's trading rules](https://www.bse.cn/jygl_list/200028217.html) specify 30% ordinarily and no limit on an IPO's first trading day or the first delisting-arrangement day. [SSE's product-information specification](https://www.sse.com.cn/services/tradingtech/data/c/10784728/files/8e09e41624bd4d63b62cd86e16e525e1.pdf) exposes per-product limit type and upper/lower prices; SZSE explicitly publishes per-security parameters through static files and realtime snapshots as above. The SSE specification cited here predates the 2026 trading-rule revision: validate the current revision before binding fields. BSE equivalent parameter-feed semantics and access remain unverified.

Therefore a production D17 `limit_up/limit_down` fact needs the day's exchange-provided parameter record (or fully versioned rule calculation with all effective-date inputs and exchange exceptions), not a hard-coded 10/20/30% guess. A price at a limit is not inherently untradeable; order-side, queue/liquidity and actual market state are separate inputs. Effective-date rule versions, ex-right reference prices, risk-warning/board status and no-limit exceptions all matter. Until these facts are covered and reconciled, return unavailable rather than fabricated eligibility.

For D17, report listing state separately as `BeforeListing`/`Listed`/`Delisted`/`Unknown`, anchored to *effective trading dates* and a no-event cutoff. Also require same-day board, risk-warning (ST), tick and limit-type/price fields with **field-level** original-source provenance; if deriving a limit, pin the rule revision and exchange rounding rule. A public listing announcement can prove a positive event but an empty list cannot prove continuing listing. Missing/partial pages, duplicate rows or conflicting exchange records must produce a typed unavailable/conflict result, never default to `Listed`, `Trading` or an ordinary limit.

## Delivery status and next proof

**Can deliver now:** this source inventory, a fail-closed evidence model and a prospective versioned interface design. **Cannot deliver now:** verified negative suspension status across SSE/SZSE/BSE, comprehensive historical listing/delisting status, or exchange-accurate per-security/date limit prices. No direct full-feed sample, access entitlement, daily completeness marker, correction replay or cross-exchange test was obtained in this research. The next proof is a small authorized pilot: obtain one exchange's daily security-information/reference file plus intraday status channel for a named date; retain raw bytes/hash and specification revision; demonstrate universe/count/trailer/sequence reconciliation, an actual halt, an ordinary tradable security and a no-event date; then repeat for each exchange before admitting `complete=true`. Public announcement pages remain corroborating evidence only.

Candidate `688277` (missing daily bars 2026-07-16 through 2026-07-29; purported resumption 2026-07-30) versus `688561` control was provided as an **unverified lead**, not independently checked here. It must not enter a production fixture or acceptance proof until official status records and the exact resumption effective date are retained.
