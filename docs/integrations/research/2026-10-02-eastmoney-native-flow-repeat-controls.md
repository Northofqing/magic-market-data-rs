## Industry selector and leader identity from the already captured JavaScript

The captured first-party [industry table script](https://data.eastmoney.com/newstatic/js/bkzj/list.js) (SHA-256 `523c796316670b0b0d3ae5385ee437a2b6b68fe0ff6dc7d66d7a61de54f82ebc`) names its board filter `bk` and maps `hy` to the literal table-filter value `m:90 s:4` (`bkvalues`, lines 1053–1056). The page labels `hy` as 行业资金流 in captured [HTML](https://data.eastmoney.com/bkzj/hy.html), lines 3616–3619. A *separate* chart handler sets `fs` to `m:90+s:4` for `hy` (script line 620), then passes it to `getbkdata` for `/dataapi/bkzj/getbkzj` (lines 644, 2066–2075). The `+` string therefore should not be substituted for the table's space-valued `fs` without observing the specific runtime request. The repository's [`BoardCategory::Industry`](../../../crates/magic-eastmoney-rs/src/board_flow.rs#L24-L27) uses `m:90+t:2`. The captured JavaScript proves that both selectors are associated with an industry-labeled presentation in their respective code, but **does not define `s:4` or `t:2`, prove equivalent membership, quantify overlap, or prove the old selector is invalid**. No industry JSON response was obtained.

The same table script maps daily `f204` to leader name and `f205` to leader code (lines 1023–1024), and its today field list requests them but omits `f206` (line 1036). Five-day and ten-day lists use **different** leader name/code fields, `f257/f258` and `f260/f261` respectively (lines 1038–1039). The repository adapter instead requests `f204,f205,f206` for every admitted interval and constructs `leader_instrument` only when it has both a six-digit leader code and an integral `f206` market; otherwise it records `None` ([parser](../../../crates/magic-eastmoney-rs/src/board_flow.rs#L152-L176)). Consequently, a response shaped only like the page's today field list would retain a possible leader name/code but yield **no exchange-bound normalized leader instrument** in the current parser. A page-shaped five-/ten-day response would not provide the adapter's requested `f204/f205` fields either. This is a field-list compatibility concern, not proof that the backend no longer serves `f206` or that a new mapping is safe. A live identity-bearing JSON control would be required before changing the contract.
